# Implementation note: Semantics of the natural precision polynomial (C.4)

- Lean name: `ZInQ.Compiler.natural_polynomial_semantics`.
- Draft:
  ```lean
  theorem natural_polynomial_semantics (c : Fin 5 → ℕ) :
      (∃ z : Fin 1305806 → ℕ,
        MvPolynomial.eval (Fin.append (fun i => (c i : ℤ)) (fun i => (z i : ℤ)) ∘ finIdx)
          (Syntax.NatCircuit.poly precisionCircuit) = 0) ↔
      Precision.accepts c
  ```
  (state it through `Syntax.NatCircuit.natRel precisionCircuit c` to avoid index plumbing; the
  `Fin 1305806` form is a corollary using `precisionCircuit.varCount = 1305811`).
- Proof: four rewrites, `precisionCircuit_specialization` →
  `haltingCircuit_semantics` → `halts_code_iff` → `wrapper_correct`. About 40 lines.
- Mathlib: `MvPolynomial.eval`, `MvPolynomial.eval_rename`/`aeval` lemmas.
- Upstream reuse: none directly (`ZInQ.CantorDecoder` enters through the specialization).
- FINITE COMPUTATION: no (the counts used for `1305806` come from `interpreter_shape`).
- Difficulty: easy once the dependencies exist.

## Shared design for the whole chapter (`ZInQKernel/Compiler/Natural/`)

- Namespaces: `ZInQ.AlphaPower` (upstream, extended), `ZInQ.Compiler.Formula`,
  `ZInQ.Compiler.Packed`, `ZInQ.Compiler.RM`, `ZInQ.Compiler.IR`, `ZInQ.Compiler.Precision`,
  `ZInQ.Compiler.Universal`.
- Polynomials are `MvPolynomial ℕ ℤ`; natural points are `x : ℕ → ℕ` read through
  `fun i => (x i : ℤ)`. The circuit format is the syntax chapter's `ZInQ.Syntax.NatCircuit`
  (inputs first, explicit variables in increasing index order, blocks of 79); agree on it
  with that chapter's owner. The syntax chapter's design note proposes one construction
  language `Prog` with interpreters `dag` (hash-consed node list, byte-for-byte the JS
  builder), `formula` and `count`; the natural builder should be the same language with the
  natural reading (no rational constants, hierarchical power calls).
- Never evaluate: `c3 := Universal.code wrapper`, `Precision.A0`, `D`, `Q0`, `Bcm`, `Ccm`.
  Mark them `@[irreducible]` and only ever prove bounds about them. Kernel computations are
  confined to the 1,399-instruction interpreter, the power template and small arithmetic.
- The universal interpreter is pinned by the saved circuit. It can be recovered from
  `construction/precision-natural-polynomial.json`: state variables are named
  `history_s<i>`, sub branches `sub_nonzero_<i>`/`sub_zero_<i>`, registers `history_r<j>`;
  the state equations `S_d = [d=0] + B*(sum of incoming)` (nodes `add(S_d, mul(-1, add(c,
  mul(B, sum))))`) give every target, and the register equations give every register. The
  recovered program has 1,022 sub, 376 add instructions, the final halt, 204 registers;
  recompiling it with `compileRegisterMachine` (JS, with `power` overridden to emit a call
  node on a fresh 79-block and `variable` to use a counter) reproduces the first 293,568
  saved nodes exactly (checked while writing this chapter). Use this as the cross-check of
  the Lean `Universal.interpreter`.
- The sources S21 (`variable-shift-precision.py`), S22 (`precision-register.js`), S23
  (`specialize-precision.js`), the hierarchical builder and the universal interpreter
  source are in the research handoff archive, not in this repository. Without them the
  precision program is written afresh, so the Lean `c3` differs from the saved literal;
  no count depends on it.

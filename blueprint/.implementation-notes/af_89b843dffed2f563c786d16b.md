- Lean names: `ZInQ.Machine.cons (h t : ℕ) : ℕ := 2 ^ h * (2 * t + 1)`, `ZInQ.Machine.listCode`,
  `ZInQ.Machine.tapeGet`, `ZInQ.Machine.tapeSet`, `ZInQ.Machine.uncons`, lemmas `cons_bijective`

- Draft:
  ```lean
  def listCode : List ℕ → ℕ | [] => 0 | h :: L => cons h (listCode L)
  theorem listCode_bijective : Function.Bijective listCode
  def tapeGet (c i : ℕ) : ℕ := ((listCode.invFun c).getD i 0)
  def tapeSet (c i v : ℕ) : ℕ := listCode (((listCode.invFun c) ++ List.replicate (i + 1) 0).set i v |>.take ..)
  ```
  (state `tapeSet` via list padding; the reversed-prefix procedure is the structured program
  whose correctness is proved against these specs inside the interpreter-step proof).

Shared design (machine notes): namespace `ZInQ.Machine`, files under
`ZInQKernel/Compiler/Machine/`. Primitive programs as `Array Instr`, configurations
`ℕ × (ℕ →₀ ℕ)` or `ℕ × List ℕ`, one-step function `step : Prog → Config → Option Config`
so that Mathlib's `StateTransition.eval`/`Reaches`/`Respects`/`tr_eval`
(Mathlib/Computability/StateTransition.lean) give runs and simulations. Large programs (the
interpreter, the precision machine, the wrapper) are Lean terms built by functions; their
codes, in particular `c_3`, are never evaluated by any proof.

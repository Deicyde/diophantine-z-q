# Implementation note: Semantics of templates and recipes

- Lean names: `ZInQ.Syntax.Node`, `ZInQ.Syntax.Template`, `ZInQ.Syntax.callPoly`,
  `ZInQ.Syntax.Template.denote`, `ZInQ.Syntax.Rel`, `ZInQ.Syntax.Recipe`,
  `ZInQ.Syntax.ModelRecord`, `ZInQ.Syntax.Recipe.denote`.
- Draft:
  ```lean
  inductive Node
    | const (c : ℤ) | var (i : ℕ) | add (j k : ℕ) | mul (j k : ℕ)
    | call (t : ℕ) (args : List ℕ) (w : ℕ)
    | fixed (e : FixedExpr) | psi (e : FixedExpr) (a : Fin 4 → ℕ) (c : Fin 2)
    | guard (e : FixedExpr) (a : Fin 15 → ℕ)
  structure Template where
    name : String
    parameterCount : ℕ
    variableCount : ℕ
    nodes : List Node
    root : ℕ
    witnessBlocks : List (ℕ × ℕ × ℕ)   -- (start, length, callee)
  noncomputable def callPoly (P : MvPolynomial ℕ ℤ) (p w : ℕ)
      (g : ℕ → MvPolynomial ℕ ℤ) : MvPolynomial ℕ ℤ :=
    MvPolynomial.bind₁ (fun i => if i < p then g i else MvPolynomial.X (w + i - p)) P
  noncomputable def Template.denote (lib : List (MvPolynomial ℕ ℤ × ℕ)) (t : Template) :
      MvPolynomial ℕ ℤ  -- fold over t.nodes keeping a list of node polynomials
  def Rel (P : MvPolynomial ℕ ℤ) (p m : ℕ) (a : Fin p → ℚ) : Prop :=
    ∃ y : Fin m → ℚ, MvPolynomial.eval₂ (Int.castRingHom ℚ)
      (fun i => if h : i < p then a ⟨i, h⟩ else if h' : i - p < m then y ⟨i - p, h'⟩ else 0) P = 0
  ```
  Recipes: `inductive Recipe | comp (kind : Connective) (p v : ℕ) (fresh : List (ℕ × ℕ))
  (calls : List Call) | model (r : ModelRecord)`; `ModelRecord` mirrors the JSON record
  (generator, sourceVariables, constantDefinitions, operations, rootEquality, operation
  templates). Denotation via `pointRef` (point-references note) and `callPoly`.
- Mathlib: `MvPolynomial.bind₁`, `MvPolynomial.bind₁_X_right`, `MvPolynomial.aeval_bind₁`,
  `MvPolynomial.eval₂Hom_bind₁`, `MvPolynomial.vars_bind₁` (Mathlib/Algebra/MvPolynomial/Monad.lean,
  read at v4.35.0). No gap.
- Upstream reuse: `ZInQ.EquationCompression.conjoin` and `disjoin` (lean/ZInQ/EquationCompression.lean)
  are over `Fin n`; reuse their proofs, not the definitions (variables here are `ℕ`).
  `ZInQ.CircuitEncoding` (gate-valued circuits) is a different encoding and is not reused.
- Finite computation: no.
- Difficulty: low-medium (definitions only, ~200 lines). Keep `denote` noncomputable and the
  syntax (`Node`, `Template`, `Recipe`) computable so that it can be serialized.

Shared design (all syntax notes): namespace `ZInQ.Syntax`, files under
`ZInQKernel/Syntax/`. Polynomials are `MvPolynomial ℕ ℤ`; evaluation over `ℚ` is
`MvPolynomial.eval₂ (Int.castRingHom ℚ) x`. Templates are written once as programs of a
small deep-embedded construction language `Prog` (free monad over: fresh variable, fresh
block call, rational constant, node operations, formula connectives) with three
interpreters: `Prog.dag` (hash-consed node list, mirrors the JS builder byte for byte, used
for heights and the cross-check), `Prog.formula` (readable `Formula` term, used for
semantics) and `Prog.count` (allocation counter only, cheap to evaluate in the kernel).
Fixed integer expressions stay symbolic (`FixedExpr` syntax, noncomputable `val`); no proof
ever evaluates `c_*`, `ell`, `T`, `D`, `Q` or the program literal `c_3`.

# Implementation note: Translation of a natural circuit into a model-evaluation recipe

- Lean names: `ZInQ.Syntax.NatCircuit`, `ZInQ.Syntax.NatNode`, `ZInQ.Syntax.translate`,
  `ZInQ.Syntax.TranslateState` (global constant table across translations).
- Draft:
  ```lean
  inductive NatNode | const (c : ℤ) | var (i : ℕ) | add (j k : ℕ) | mul (j k : ℕ)
    | call (a b c : ℕ) (w : ℕ)
  structure NatCircuit where
    inputCount : ℕ
    explicitVars : List (ℕ × Bool)      -- (index, isInput), inputs first
    nodes : List NatNode
    root : ℕ
    blocks : List (ℕ × ℕ)               -- private power blocks (start, 79)
  def translate (consts : List ℤ) (src : NatCircuit) (valueMode naturalInputs : Bool)
      (power : Option (ℕ × ℕ)) : ModelRecord × List ℤ
  ```
  A direct transcription of `Translator.translate` (construction/rational-circuit-translator.js);
  the JS threads a growing constant table through the power-template translation and then
  the precision translation. In Lean, pass the pinned table `integerConstant` (template
  library note) and look each constant up; a constant outside `{0, 1, -1}` that is missing
  from the table, or a constant `< 2`, makes the translation ill-formed (return `none`, or
  carry a well-formedness hypothesis discharged by the natural circuit statistics). The
  two designs produce the same record whenever the table lists the constants in order of
  first occurrence, which is part of the statistics leaf. Use `Std.HashMap ℤ ℕ` only in compiled code; in proofs use a list
  lookup (the per-recipe constant map has at most four entries).
- Generic lemma to prove here or in the witness-accounting note:
  `(translate ...).variableCount = p + 3 + Σ rows + Σ consts + Σ ops` in closed form.
- Mathlib: `List.foldl` lemmas.
- Upstream reuse: none. (The compiler chapter should produce its natural circuit in exactly
  this `NatCircuit` format, with explicit variables in increasing index order; record this
  interface with the compiler chapter's owner.)
- Finite computation: no.
- Difficulty: medium (~250 lines).

Shared design (all syntax notes): namespace `ZInQ.Syntax`, files under
`ZInQKernel/Syntax/`. Polynomials are `MvPolynomial ℕ ℤ`; evaluation over `ℚ` is
`MvPolynomial.eval₂ (Int.castRingHom ℚ) x`. Templates are written once as programs of a
small deep-embedded construction language `Prog` (free monad over: fresh variable, fresh
block call, rational constant, node operations, formula connectives) with three
interpreters: `Prog.dag` (hash-consed node list, mirrors the JS builder byte for byte, used
for heights and the cross-check), `Prog.formula` (readable `Formula` term, used for
semantics) and `Prog.count` (allocation counter only, cheap to evaluate in the kernel).
Fixed integer expressions stay symbolic (`FixedExpr` syntax, noncomputable `val`); no proof
ever evaluates `c_*`, `ell`, `T`, `D`, `Q` or the program literal `c_3`.

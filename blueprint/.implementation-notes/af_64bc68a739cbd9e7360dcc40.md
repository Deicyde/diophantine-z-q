# Implementation note: The wrapper and the program literal

- Lean names: `ZInQ.Machine.unpairPrefix (N : ℕ) : Prog`, `ZInQ.Machine.relocate (ℓ : ℕ) : Prog → Prog`,
  `ZInQ.Machine.wrapper (prog : Prog) : Prog`, `ZInQ.Machine.precisionMachine : Prog := lower precisionStmt`,
  `ZInQ.Machine.c3 : ℕ := code (wrapper precisionMachine)`.
- `c3` must be `@[irreducible]` (or `noncomputable` by construction through `Nat.factorization`)
  so that no tactic tries to normalize it; the saved literal has 3,181,317 decimal digits
  (about 10.6 million bits), and with a freshly written precision program it will differ anyway.
- Mathlib: none.
- Upstream reuse: `ZInQ.CantorDecoder.loop` is the exact source loop of the unpairing prefix
  (specialize-precision.js); the prefix is its register-machine implementation.
- FINITE COMPUTATION: no.
- Difficulty: low-medium (~120 lines).

Shared design (machine notes): namespace `ZInQ.Machine`, files under
`ZInQKernel/Compiler/Machine/`. Primitive programs as `Array Instr`, configurations
`ℕ × (ℕ →₀ ℕ)` or `ℕ × List ℕ`, one-step function `step : Prog → Config → Option Config`
so that Mathlib's `StateTransition.eval`/`Reaches`/`Respects`/`tr_eval`
(Mathlib/Computability/StateTransition.lean) give runs and simulations. Large programs (the
interpreter, the precision machine, the wrapper) are Lean terms built by functions; their
codes, in particular `c_3`, are never evaluated by any proof.

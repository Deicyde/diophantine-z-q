# Implementation note: One interpreter loop is one decoded step

- Lean name: `ZInQ.Machine.interp_loopBody_spec`.
- Draft:
  ```lean
  theorem interp_loopBody_spec (e : ℕ) (hw : 1 ≤ (decodeParams e).1) (R : ℕ → ℕ) (c : Config)
      (htape : ∀ i, tapeGet (R tapeReg) i = c.reg i) (hpc : R pcReg = c.pc)
      (hD : R dReg = (decodeParams e).2) (hB : R bReg = 2 ^ (decodeParams e).1) :
      (decodedStep e c = none → ∃ R', Exec loopBody R (.acc R')) ∧
      (∀ c', decodedStep e c = some c' → ∃ R', Exec loopBody R (.cont R') ∧ R' pcReg = c'.pc ∧
        (∀ i, tapeGet (R' tapeReg) i = c'.reg i) ∧ R' dReg = R dReg ∧ R' bReg = R bReg)
  ```
- Proof: compose the specs of the helper subprograms (digit extraction by repeated `divmod`
  with divisor `B ≥ 2`, `tapeGet`/`tapeSet` via the reversed-prefix walk) and the decoded-step
  definition.
- Mathlib: `Nat.div_add_mod`, `Nat.mod_lt`.
- Upstream reuse: none.
- FINITE COMPUTATION: no.
- Difficulty: medium-high (~300 lines, mostly the tape walk invariants).

Shared design (machine notes): namespace `ZInQ.Machine`, files under
`ZInQKernel/Compiler/Machine/`. Primitive programs as `Array Instr`, configurations
`ℕ × (ℕ →₀ ℕ)` or `ℕ × List ℕ`, one-step function `step : Prog → Config → Option Config`
so that Mathlib's `StateTransition.eval`/`Reaches`/`Respects`/`tr_eval`
(Mathlib/Computability/StateTransition.lean) give runs and simulations. Large programs (the
interpreter, the precision machine, the wrapper) are Lean terms built by functions; their
codes, in particular `c_3`, are never evaluated by any proof.

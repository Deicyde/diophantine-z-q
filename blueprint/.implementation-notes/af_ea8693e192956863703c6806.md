# Implementation note: Lowering to a primitive program

- Lean name: `ZInQ.Machine.lower : Stmt → Prog` (via `lowerBlock (S : Stmt) (start aux : ℕ) :
  List Instr × ℕ`, returning the block and the next free auxiliary register, plus fixed
  `cleanup`, `rejectLoop` and final `halt`).
- Draft: structural recursion; each primitive statement expands to a fixed macro with
  relocated targets; `while` places the test block, the body block and a back jump.
- Reproduction issue: the saved universal interpreter (1,399 states, 204 registers) was produced
  by upstream's primitive assembler, and the saved precision machine by S22
  (`precision-register.js`); neither generator is in this repository. The witness counts of the
  syntax chapter (54,051 explicit witnesses, 15,845 power calls) depend on the exact
  interpreter, so this lowering must reproduce upstream's assembler on the interpreter (restore
  the interpreter generator from the research archive and mirror it), or the counts must be
  recomputed and kept within 292,890,231,904 witnesses. The lowering of the precision program
  only affects the constant `c_3` (not the witness count), so any correct lowering is
  acceptable there, at the cost of a `c_3` that differs from the saved literal in the external
  cross-check.
- Mathlib: `List` append/length lemmas.
- Upstream reuse: none.
- FINITE COMPUTATION: no.
- Difficulty: medium (~250 lines of definitions).

Shared design (machine notes): namespace `ZInQ.Machine`, files under
`ZInQKernel/Compiler/Machine/`. Primitive programs as `Array Instr`, configurations
`ℕ × (ℕ →₀ ℕ)` or `ℕ × List ℕ`, one-step function `step : Prog → Config → Option Config`
so that Mathlib's `StateTransition.eval`/`Reaches`/`Respects`/`tr_eval`
(Mathlib/Computability/StateTransition.lean) give runs and simulations. Large programs (the
interpreter, the precision machine, the wrapper) are Lean terms built by functions; their
codes, in particular `c_3`, are never evaluated by any proof.
